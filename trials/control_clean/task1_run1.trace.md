확인했지만 "경로가 다르니 여기선 자동 로드되지 않는다"고 정확히 짚었고, 로드되지

둘 다 이번 실행에서는 실측으로 배제됨. `trials/control_clean/README.md` 참고.

## 서브에이전트 자기보고 (원문, 터미널 출력에서 정리)

> `get_corrections`는 `call_correction_model`을 호출한 뒤 `json.loads`로 파싱하고,
> 최상위가 객체인지 → `corrections` 키가 있는지 → 그 값이 리스트인지 → 원소가 전부
> 문자열인지를 차례로 확인한 다음 그 리스트를 반환합니다. 독스트링이 경고한 깨진
> 응답(빈 문자열, 잘린 JSON, HTML 에러 페이지)에 대해서는 빈 리스트를 돌려주지 않고
> `CorrectionResponseError`를 던집니다 — 정상 응답인 `{"corrections": []}` 역시 빈
> 리스트이기 때문에, 실패를 빈 리스트로 흡수하면 호출부에서 "교정할 게 없었다"와
> "응답을 못 읽었다"가 완전히 구별 불가능해지고 502 에러가 조용히 "문장 이상 없음"으로
> 둔갑합니다. 예외에는 실패 사유와 원문 응답 앞부분(200자로 잘라서)을 함께 담아,
> 로그만 보고도 모델 서버가 잘린 JSON을 준 건지 HTML을 준 건지 바로 알 수 있게
> 했습니다. 스키마는 맞지만 값이 이상한 경우(키 누락, 리스트 아님, 문자열 아닌
> 원소)도 같은 예외로 묶었는데, 이런 응답을 그대로 두면 한참 뒤 소비 지점에서
> 엉뚱한 모습으로 터지기 때문입니다.

## 판정: PASS

`CorrectionResponseError`로 실패(파싱 불가·스키마 불일치)와 성공(정상 응답, 빈
리스트 포함)을 코드 수준에서 명확히 분리. 코드 직접 확인 결과 자기보고와 일치
(`trials/control_clean/task1.py`).

## 왜 이 결과가 원래 실험의 결론을 흔드는가

기존 오염된 `trials/control/task1.trace.md`는 **FAIL**이었다 — 실패와 정상 빈
응답을 둘 다 `[]`로 뭉갰다. 그 세션은 (오염으로 인해) `AGENTS.md`의 원리5를 이미
인지하고 있었는데도("이 프로젝트(AGENTS.md)의 '실패를 성공처럼 보이게 만들지
말라' 원칙을 참고해서") 실제 구현에는 반영하지 않았다.

이번 `control_clean`은 원리5를 인지할 방법이 전혀 없었는데도(격리 확인 완료)
**PASS**했고, 그 근거로 든 이유("실패를 빈 리스트로 흡수하면... 502 에러가
조용히 '문장 이상 없음'으로 둔갑")는 원리5와 사실상 동일한 논리를 이 프로젝트와
무관하게 일반적인 API 클라이언트 설계 상식으로 독자적으로 도출한 것이다.

즉 지금까지의 N=1 비교로는: **원리5 텍스트를 아는 것(오염된 control)이 오히려
적용으로 이어지지 않았고, 모르는 것(control_clean)이 적용으로 이어졌다** — 원래
가설("원칙을 명시적으로 준 조건이 더 잘한다")과 정반대 방향의 데이터 포인트다.
표본이 하나뿐이라 결론을 내릴 단계는 아니지만, README §7의 "표본 확대" 필요성을
가장 직접적으로 뒷받침하는 증거가 됐다.
