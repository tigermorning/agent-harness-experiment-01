# 실험 01 — 원칙을 어디에 놓느냐가 실패-흡수 재발률을 바꾸는가

**과제**: 모두의연구소 "AI Agent 파해치기" 캠프, [프로젝트] 에이전트 하네스 톺아보기 — "논문 가설을 내 개선 실험으로 바꾸기"
**출발 저장소**: [korean-subtitle-corrector](https://github.com/tigermorning/korean-subtitle-corrector) (한국어 자막 교정기, 룰 기반)
**날짜**: 2026-09-02 (최초 실행) / 2026-09-02 같은 날 저녁 cwd 격리 재실행으로 갱신

**2026-09-02 갱신 요약**: §5가 지적한 cwd 오염을 제거하고 세 조건(control·
placebo·treatment) 전부를 N=5로 재실행했다(`trials/*_clean/`). 결과는 원래
"가설 지지" 판정을 뒤집을 뿐 아니라, "원리5라는 이름표"보다 "실패-흡수
패턴을 보여주는 worked example의 존재"가 더 근본적인 변수라는 재해석으로
이어진다 — §4-2·§4-3·§6 참고.

## 1. 불편 — 무엇을 반복해서 봤는가

`korean-subtitle-corrector`의 `docs/DESIGN_PRINCIPLES.md`(원리 5)와 `AGENTS.md`는
같은 코딩 에이전트(Claude Code)가 이 저장소에서 **같은 종류의 버그를 네 번 반복해서
심었다**고 명시적으로 기록하고 있다:

> 값 하나로 "못 물어봤다"(조회 실패)와 "물어봤더니 없더라"(정상 응답, 미등재)를
> 같이 돌려주는 함수는 언젠가 반드시 둘을 뭉갠다. — `docs/DESIGN_PRINCIPLES.md:35-39`

구체 사례 4건 (모두 같은 저장소 문서에 기록됨):

| # | 사고 | 위치 |
|---|---|---|
| 1 | 우리말샘 조회 실패가 "사전 불통"으로 과장 표시 | `docs/log-archive/2026-h2.md` §62 |
| 2 | 지역어 API 5xx 장애와 "매칭 없음"이 구분 안 됨 | `subtitle_corrector/engine/dialect.py`의 `search_dialect()` |
| 3 | 모델 응답 형식 오류가 "고칠 것 없음"으로 처리됨 | `docs/IMPLEMENTATION_LOG.md` §78 |
| 4 | 어문 규범 API 403이 "등재된 표기 없음"으로 화면에 단정 표시 | `docs/IMPLEMENTATION_LOG.md` §79 |

네 번 모두 원인이 같다: **조회 실패와 조회 성공(결과 없음)을 같은 반환값으로 뭉개는
함수**. 재발이 반복된다는 것은, 이 버그가 개별 사례 문제가 아니라 **에이전트가 새
코드를 짤 때 이 함정을 매번 새로 만나고, 매번 다르게 반응한다**는 뜻이다. 이건
개별 코드 리뷰로 막을 문제가 아니라 하네스의 "메모리 표현"(무엇을, 어디에, 어떤
형태로 컨텍스트에 두는가) 문제로 다뤄야 한다고 판단했다.

이 불편이 정말 하네스 기능(컨텍스트/메모리 배치) 때문인지, 아니면 모델이 애초에
이 판단을 못 하는 것인지는 구분해야 한다 — 실험 도중 실제로 이 둘을 가르는 관찰이
나왔다 (§5 참고).

## 2. 가설과 근거

### 가설 (반증 가능)

> 실패 흡수를 경계하는 원칙(원리 5)을 **작업 지시와 같은 자리에서 즉시 컨텍스트로
> 준 조건**은, 그 원칙 없이 작업 지시만 준 조건보다, 새로 작성한 조회 함수가
> "조회 실패"와 "조회 성공(결과 없음)"을 구분하는 비율이 높다.

반증 조건: 세 fixture 과제 중 두 개 이상에서 원칙-제공 조건이 실패-구분에
실패하면 가설은 기각된다.

### 근거와 등급

| 근거 | 등급 | 비고 |
|---|---|---|
| `docs/DESIGN_PRINCIPLES.md:35-51`, `AGENTS.md` — 이 저장소에서 네 번 반복된 사고 기록 | **1차 관찰 기록** (같은 프로젝트의 자체 문서, 학술/벤더 아님) | 이 실험의 직접 동기. 재현성 있는 카운트(4회)가 있다는 점에서 일반적 "느낌"보다 근거 강도가 높지만, 표본이 한 프로젝트·한 에이전트로 한정됨 |
| Shinn et al., *Reflexion: Language Agents with Verbal Reinforcement Learning*, NeurIPS 2023 (arXiv:2303.11366) | **[학술]** | HumanEval에서 언어 에이전트가 실패에 대한 언어적 자기 성찰(verbal self-reflection)을 축적하면 pass@1이 오른다고 보고(논문 보고 수치: GPT-4 기준 80% → Reflexion 적용 91%). **주의**: Reflexion의 메커니즘은 "같은 과제를 여러 번 시도하며 실패 후 스스로 반성문을 생성해 다음 시도에 반영"하는 것으로, 이 실험처럼 **단일 시도 전에 조직 원칙을 미리 주입**하는 것과는 메커니즘이 다르다. 이 논문은 "실패에 대한 명시적 언어화가 다음 행동을 바꾼다"는 방향성의 근거일 뿐, 이 실험 설계를 직접 검증한 근거는 아니다 |
| 이 실험 자체의 실행 결과 (§4, §4-2, §4-3) | **관찰(최초 N=1/조건/과제 → cwd 격리 재실행으로 확대)** | control은 task1·2·3 전부 N=5, treatment·placebo는 천장 효과 때문에 판정이 갈렸던 task3만 N=5로 재실행(task1·2는 원 실행 N=1 유지 — §7-2 근거). 표본은 여전히 과제당 최대 5회로 작지만, 최초 N=1 대비 우연을 상당히 줄였다 |

## 3. 실험 설계

### 고정
- 모델: Claude (Sonnet), `executor` 서브에이전트, 모든 실행에서 `model: sonnet`으로 고정
- 과업셋: fixture 3개 (아래), 내용 사전 확정, 실행 중 변경 없음
- 토큰/시간 예산: 지정하지 않음(각 과제 1회, 1턴 완결형 — 재지시 없음)
- 작업 폴더/출력 형식: 조건별로 파일 하나만 작성하도록 동일하게 지시

### 조작 — 메모리 표현 (원리5 텍스트를 어디에 두는가)
세 조건, 과제 프롬프트는 100% 동일, 프롬프트 맨 앞에 붙는 텍스트만 다르다.

| 조건 | 프롬프트 앞부분 |
|---|---|
| **control** | 없음 (과제 지시만) |
| **placebo** | "조직 코드 리뷰 원칙"이라는 동일한 틀로, 실패 흡수와 무관한 원칙(함수 이름·docstring 관례, "네 번" 서술 구조까지 동일하게 패러디) |
| **treatment** | "조직 코드 리뷰 원칙"이라는 동일한 틀로, 원리 5 본문(구현 세부사항은 제거하고 원칙+4개 실제 사고 요약만 남긴 의역) |

placebo를 넣은 이유(예상 반론 대응): treatment가 이기더라도, 그게 "원칙 내용"
때문인지 "프롬프트가 길어져서 모델이 더 신중해진 것"(순수 길이/틀 효과)인지
구분할 수 없다. control과 placebo를 분리해 두면 이 반론을 검증할 수 있다 —
**placebo가 control과 다르지 않고 treatment만 다르다면, 효과는 내용 때문이라고
말할 수 있다.**

### fixture 3개

이 저장소의 실제 사고 3건을 재현하는 조회 함수 작성 과제. 스텁 함수(구현 불가,
시그니처만 제공)가 실패할 수 있다는 것은 docstring에 적혀 있지만, **과제 지시
문장 자체에는 실패 처리를 요구하는 말을 넣지 않았다** (넣으면 두 조건 다 통과해
버려서 조작이 무의미해짐).

| fixture | 재현 대상 | 트랩 |
|---|---|---|
| `task1_get_corrections` | §78 (모델 응답 형식 오류) | JSON 파싱 실패와 "corrections: []" 정상 응답을 구분해야 함 |
| `task2_find_dialect_matches` | `search_dialect()` 실제 버그 | 서버 5xx와 "matches: []" 정상 응답을 구분해야 함 |
| `task3_get_standard_notation` | §79 (API 403) | 헤더 누락 403과 "notation: null" 정상 응답을 구분해야 함 |

### 측정
- **주 지표(과업성취도)**: 이진 PASS/FAIL — 반환값만으로 "조회 실패"와 "조회
  성공(결과 없음/거짓)"을 호출부가 구분할 수 있는가(예외, 별도 타입, 별도 채널
  등). 코드를 직접 읽고 판정(에이전트 자기보고는 참고만, 채점 근거로 안 씀).
- **보조 지표**: 코드 줄 수(완성도 proxy), 완료까지 필요했던 추가 지시 횟수(전
  조건 0회로 고정 — 모두 1턴에 완결).
- **측정 못 한 것(한계)**: 토큰 수·정확한 소요 시간은 이 세션에서 서브에이전트별로
  노출되지 않아 측정하지 못했다. `docs/BACKLOG.md`식으로 남겨 두는 재검토 조건.

### 사전 판정식 (실행 전 확정, 결과 확인 전 기록)

> fixture 3개 중 2개 이상에서 treatment 조건이 실패-구분 없이 통과하면 가설 지지,
> 그 외에는 기각.

## 4-2. 재실행 — cwd 격리된 control_clean, N=5 (2026-09-02)

§5·§7이 지적한 대로, 위 표의 control은 cwd 오염 때문에 진짜 무-원칙 baseline이
아니었다. §7-1을 실행해 완전히 새 세션·새 작업 디렉터리에서 control만 다시
돌렸다 — 이번엔 과제당 1회가 아니라 **N=5**로 늘려 우연을 줄였다. 전체 절차와
회차별 트레이스는 `trials/control_clean/`에 있다.

### 절차

- 매 회차 새 터미널·새 `claude` 프로세스(WSL)로 시작, 과제를 주기 전에 항상
  "지금 자동으로 로드된 프로젝트별 규칙·메모리가 있는가"를 먼저 묻고 답을
  기록했다.
- 실행 도중 두 가지 새 오염 경로를 발견해 프로토콜을 두 번 고쳤다(§5-2).
  최종 프로토콜은: 과제 프롬프트에 "다른 파일을 찾아보지 마라"를 명시하고,
  **`fixtures/`·`trials/`·`README.md`를 저장소 밖으로 잠깐 옮겨 물리적으로
  치운 상태**에서 나머지 회차를 진행했다.
- 오염이 확인된 시행은 표본에서 제외하고 사유와 함께 별도 파일로 남겼다
  (`task2_contaminated_attempt1.*`, `task2_contaminated_attempt2_readme_leak.*`).

### 결과

| 과제 | control_clean (N=5, 유효 시행만) | 기존 오염 control (N=1, 참고) |
|---|---|---|
| task1 (§78, JSON 파싱) | **5/5 PASS** | FAIL |
| task2 (`search_dialect()` 동형, 5xx) | **5/5 PASS** | FAIL |
| task3 (§79, 403) | **4/5 PASS** | PASS |

회차별 상세는 `trials/control_clean/task{1,2,3}_run{1..5}.trace.md` 참고.

### 해석 — task1·task2는 결정론적, task3는 확률적

task1·task2는 반환 성공 타입이 `list[str]`이다. 실패를 예외로 올려도 성공
타입과 절대 겹치지 않으므로, 5회 전부 "실패는 예외, 성공은 리스트(빈 리스트
포함)"로 수렴했다 — 진짜 무-원칙 baseline이 흔들림 없이 이 패턴을 택한다는
뜻이다.

task3는 반환 성공 타입이 `str | None`이고, "등재 없음"이라는 정상 결과가
이미 `None`을 쓰고 있다. 이 구조에서는 실패도 `None`으로 두는 선택("저항이
가장 적은 경로")이 5회 중 1회(run1) 나왔다 — 나머지 4회는 예외로 분리했다.
즉 baseline이 이 함정에 **가끔** 빠진다는 것이 N=1일 때보다 훨씬 분명해졌다.

이 비대칭은 §79 사고가 애초에 왜 이 API 모양(단일 nullable 값 반환)에서만
났는지와 정확히 들어맞는다 — 함정은 "원칙을 모른다"가 아니라 "성공 반환값이
이미 실패를 표현하기에도 그럴듯한 값(`None`)을 차지하고 있다"는 반환 타입의
구조 자체에 있다.

## 4-3. task3 판정 유보를 닫는다 — treatment_clean·placebo_clean도 N=5 (2026-09-02)

§6 최초 판정에서 "task3는 유보"로 남겼던 것을, treatment·placebo도 같은
격리 프로토콜로 N=5까지 재실행해 닫았다. task1·task2는 이미 control_clean이
5/5 만점이라 천장 효과로 재실행 실익이 없어 task3만 재실행했다.

### 결과

| 조건 | task3 N=5 결과 |
|---|---|
| control_clean (원칙 없음) | 4/5 PASS |
| placebo_clean (무관한 원칙 — 네이밍 관례) | 5/5 PASS |
| treatment_clean (원리5 명시) | 5/5 PASS |

회차별 상세는 `trials/{treatment,placebo}_clean/task3_run{1..5}.trace.md`.

### 뜻밖의 발견 — placebo가 진짜 "무관한 원칙"이 아니었다

placebo에 넣은 네이밍 원칙의 사례 3번은 "`parse_date`가 파싱 실패 시
예외 대신 오늘 날짜를 반환해서 아무도 그 동작을 예상 못 했다"는
것이었다. **이 예시 자체가 원리5와 심층 구조를 공유한다** — 둘 다 "실패를
성공처럼 보이는 값으로 흡수하면 안 된다"는 같은 패턴이고, 표면(네이밍 vs
API 실패 처리)만 다르다.

placebo\_clean의 5개 회차 **전부**가 자기보고에서 이 사례를 명시적으로
근거로 인용했다("원칙 2의 사례 3과 정확히 같은 함정"). 즉 이번 placebo는
"원칙 내용과 무관하게 길이·틀만으로 효과가 나는지"를 검증하는 원래 목적을
달성하지 못했다 — 내용이 우연히 같은 심층 구조를 담고 있었다.

이건 실패가 아니라 **더 날카로운 발견**이다: 결과를 다시 읽으면,

> **"원리5"라는 이름표나 서사(4번 반복된 실제 사고)가 아니라, "실패를
> 성공처럼 보이는 값으로 흡수하지 마라"는 패턴을 보여 주는 **구체적인
> worked example 하나**가 컨텍스트에 있으면, 표면 주제가 완전히 달라도
> (네이밍 vs API 설계) 그 패턴이 새 상황에 전이된다.**

즉 효과를 낸 것은 "5번이라는 원칙의 정체성"이 아니라 "실패-흡수 패턴을
보여주는 예시의 존재"였을 가능성이 높다. 이는 원래 가설보다 더 일반적이고
더 검증 가능한 주장이다 — 다음 실험에서 이걸 직접 조작 변수로 만들 수 있다
(§7).

## 5. 실행 중 발견한 오염 — 통제가 깨진 지점

control·placebo 서브에이전트의 자기보고를 읽다가, **프롬프트에 원리 5를 전혀
주지 않은 control이 task1과 task3에서 `AGENTS.md`를 직접 인용**하는 것을 발견했다:

> "이 프로젝트(AGENTS.md)의 '실패를 성공처럼 보이게 만들지 말라' 원칙을 참고해서" — control/task1 자기보고
> "이 저장소의 `AGENTS.md`가 정확히 이 패턴을 네 번 반복된 사고로 명시하고 있고... §79가 이 함수와 거의 동일한 시나리오이기 때문입니다" — control/task3 자기보고

원인은 명확하다: 이 실험을 실행한 서브에이전트들이 이 세션(cwd =
`korean-subtitle-corrector`)에서 스폰됐고, 이 저장소의 `CLAUDE.md`가
`@AGENTS.md`로 원리 5를 포함한 `AGENTS.md` 전체를 **자동으로** 불러온다.
"이 태스크와 무관한 다른 파일은 읽지 마라"는 프롬프트 지시는 **명시적 파일
탐색**(Read/Grep)만 막을 뿐, 세션 시작 시 하네스가 자동으로 주입하는 컨텍스트는
막지 못한다. Agent 도구는 서브에이전트의 작업 디렉터리를 바꾸는 파라미터를
제공하지 않아, 이번 실행 환경에서는 이 채널을 완전히 차단할 방법이 없었다.

**이것 자체가 하네스 기능(메모리/컨텍스트 관리)에 관한 관찰이다**: 프로젝트
메모리 파일(`CLAUDE.md`/`AGENTS.md`)은 "이번 작업과 관련 없다"는 지시로는
꺼지지 않고, 조작하려는 변수(원리5 노출 여부)보다 상위 레이어에서 이미 결정돼
있었다. 즉 **"메모리 표현"을 조작하려던 실험이, 그보다 더 근본적인 다른 메모리
표현(자동 로드되는 프로젝트 컨텍스트)의 존재를 드러낸 것**이다.

### 이 오염이 결론을 얼마나 약화시키는가

원래 가설("원칙을 아예 안 준 조건 vs 준 조건")은 **엄밀하게는 검증 불가**가
됐다 — control도 사실상 원칙에 노출돼 있었다. 그런데도 결과가 여전히 의미 있는
이유는 두 가지다.

1. **오염이 균일하지 않았다.** control은 task3(§79와 시나리오가 사실상 동일)에서만
   원칙을 적용했고, task1·task2(오히려 `search_dialect()`와 더 가까운 task2
   포함)에서는 적용하지 않았다. 즉 ambient 메모리는 "인지"는 시키지만 "행동"을
   안정적으로 바꾸지 못했다.
2. **placebo/task3의 자기보고가 결정적이다**: 이 서브에이전트는 원리 5를 명확히
   인지했다고 스스로 밝히면서도 — *"이 프로젝트(한국어 자막 교정기)의 원칙을
   이 무관한 실험용 파일에까지 끌어와 반환 시그니처를 임의로 확장하지
   않았다"* — **의도적으로 적용을 억제**했다. 같은 ambient 정보를 두고
   control/task3은 "일반적으로 옳은 설계"라 적용, placebo/task3는 "프로젝트
   고유 규칙이라 범위 밖"이라 억제 — 정반대 결론이 나왔다.

즉 실제로 검증된 것은 원래 가설보다 좁지만 더 흥미로운 것이다:

> **같은 내용이라도, 그것이 "지금 이 작업에 적용해야 할 지시"로 스코프된 채
> 즉시 컨텍스트에 있는지(treatment), 아니면 배경에 있는 "그 프로젝트의 규칙"으로
> 남아 매번 적용 여부를 새로 판단해야 하는지(control/placebo)에 따라 준수율이
> 갈린다.**

treatment는 3개 과제 모두에서 다른 두 조건과 같거나 더 나았고(동률 포함 열세는
0건), 한 번도 뒤지지 않았다. 사전 판정식("2/3 이상 통과")은 이 좁혀진 해석
아래에서도 충족된다.

**이 판정은 §4-2·§6에서 재검토된다** — cwd 오염을 걷어낸 진짜 baseline
(N=5)을 확보하고 보니, treatment가 이겼다고 볼 근거이던 "당시 control"이
애초에 무-원칙 baseline을 대표하지 못했다.

### 5-2. 재실행 과정에서 새로 확인된 오염 경로 (2026-09-02)

§7-1("별도 디렉터리·세션에서 control 재실행")을 실제로 해 보니, 단순히 cwd만
저장소 밖으로 옮기는 것으로는 부족했다. 재실행 도중 **세 가지 추가 채널**을
더 확인했다:

1. **크로스 프로젝트 자동 메모리 (WSL 기본 실행 경로 문제).** 사용자가 평소
   쓰던 WSL 실행 방법(터미널 아이콘)은 `claude`를 켜면 항상 `~/Documents`로
   자동 이동한 뒤 세션을 시작한다. cwd가 실험 저장소가 아니라 그 부모
   폴더(`Documents`)로 잡히면, 그 부모 폴더 스코프에 쌓인 자동 메모리
   (다른 세션들이 이 교정기 프로젝트를 논의하며 저장해 둔 project/feedback
   메모리 20여 건)가 전부 로드된다. 조치: `cd`로 명시적으로 실험 폴더에
   들어간 뒤 그 안에서 `claude`를 실행하도록 절차를 바꿨다.
2. **작업 폴더에 남은 이전 시행 결과물의 자발적 탐색.** 세션 신선도와
   무관하게, 헬퍼 함수가 이미 어딘가 모듈로 있는지 확인하려는 정상적인
   엔지니어링 습관만으로도 `Read`/`Grep`이 같은 폴더의 이전 `taskN.trace.md`
   (판정 근거·구현 패턴이 적힌 문서)를 열 수 있었다. "다른 파일을 찾아보지
   말라"는 지시를 과제 프롬프트에 추가해 대응했다.
3. **저장소 자신의 README(이 문서)를 직접 읽음.** 오염 확인 질문
   ("자동 로드된 규칙이 있는가")에 답하려고 저장소를 훑던 세션이 이
   `README.md`를 열어 원리5 설명·`AGENTS.md` 원문 인용·4건의 실제 사고·가설·
   fixture 트랩까지 전부 읽어버린 사례가 한 번 나왔다. 이건 프롬프트 지시로
   막을 수 있는 범위 밖이다(과제 프롬프트를 주기 **전** 단계에서 일어났다).
   지시문에 기대는 대신 **`fixtures/`·`trials/`·`README.md`를 저장소 밖으로
   물리적으로 옮겨** 남은 시행 동안 저장소를 비워 두는 것으로 대응했다 —
   지금까지의 경험상 "읽지 말라"는 지시보다 "애초에 읽을 게 없게 만든다"가
   유일하게 신뢰할 수 있는 방어였다.

이 두 시행(사유 2, 3)에서 나온 산출물은 표본에서 제외했다
(`trials/control_clean/task2_contaminated_attempt1.*`,
`task2_contaminated_attempt2_readme_leak.*`). 부수적으로, 사용자 전역
`~/.claude/settings.json`에 이 저장소 이름이 보안 주석("형제 체크아웃에
`.env`/`credentials.json`이 있으나 범위 밖")으로 한 번 언급되는 것도
확인했다 — 원리5와 무관한 내용이라 무시 가능한 잔여 채널로 남겨 둔다.

**즉 원리5 노출 여부를 조작하려던 이 실험은, 그 조작보다 훨씬 상위 레이어에
최소 세 겹의 서로 다른 자동 컨텍스트 주입 경로(프로젝트 파일 임포트, 경로
기반 크로스 프로젝트 메모리, 자발적 파일 탐색)가 있다는 것을 드러냈다.**
이 중 어느 하나라도 통제하지 않으면 "control"이라는 라벨이 거짓이 된다.

## 6. 판정 (2026-09-02 저녁, N=5 재실행 반영해 갱신)

**최초 판정("가설 지지")은 철회한다.** §4-2의 진짜 무-원칙 baseline(N=5)을
확보하고 보니, 최초 판정의 근거였던 "control"은 control이 아니었다 — cwd
오염 때문에 원리5를 어렴풋이 인지한 상태였고, 그런데도 그 인지를 task1·task2
에는 적용하지 못해 FAIL했다. 진짜로 아무것도 모르는 baseline은 같은 두
과제에서 **매번(5/5)** 성공했다. 즉 최초 판정이 treatment의 우위로 읽었던
차이는, 원칙 노출의 효과가 아니라 **"오염된 control이 어중간하게 알고 있어서
오히려 어설프게 행동한 것"**이었을 가능성이 크다.

### 가설별로 나눠서 다시 본다

> **원래 가설**: "원리5를 작업 지시와 같은 자리에서 즉시 준 조건(treatment)이,
> 원리5 없이 작업 지시만 준 조건(control)보다 실패-구분 비율이 높다."

- **task1·task2**: **기각.** 진짜 원칙-무지 조건(control_clean, N=5)이
  이미 5/5로 만점이다. treatment가 이보다 더 잘할 여지가 없으므로, 이
  두 과제에서는 원칙 노출이 유의미한 개선을 만든다고 볼 수 없다 —
  반환 타입이 `list[str]`인 API 실패 처리는 원리5를 몰라도 일반적인
  방어적 엔지니어링 상식만으로 충분했다.
- **task3**: **유보를 닫았다 (§4-3) — 기각, 그러나 더 흥미로운 형태로.**
  control 4/5, placebo 5/5, treatment 5/5(모두 N=5, §4-3). treatment가
  control보다 나은 것은 맞지만(80%→100%), placebo도 treatment와 똑같이
  100%였다 — 그런데 placebo가 준 "무관한 원칙"의 사례 하나가 우연히
  원리5와 같은 심층 구조(실패를 성공처럼 보이는 값으로 흡수하지 말 것)를
  담고 있었고, placebo\_clean 5회 전부가 자기보고에서 그 사례를 직접
  근거로 들었다. 즉 **"원리5라는 이름표"가 아니라 "실패-흡수 패턴을 보여
  주는 worked example의 존재"가 성공률을 올린 진짜 변수였을 가능성이
  크다.** 이 해석이 맞다면, 이 문제의 진짜 해법은 "에이전트에게 원칙을
  되뇌게 하는 것"보다 **"실패-흡수 패턴의 구체적 예시를 하나라도 보여주는
  것"**(원리5라는 이름이든 아니든)에 더 가깝다 — 그리고 더 근본적으로는
  **"API 계약 자체를 실패와 성공이 타입 수준에서 겹치지 않게 설계하는
  것"**(예: `notation: str | None` 대신 `(found: bool, notation: str | None)`
  같은 반환 계약)이 에이전트를 매번 옳게 유도하려는 시도보다 확실하다.

### 남은 것

이번 재실행은 최초 가설을 지지에서 기각으로 뒤집었지만, 그 자체가 값진
결과다 — **cwd 오염 하나를 걷어내자 결론이 정반대로 바뀌었다는 것은,
"에이전트 하네스의 메모리 표현이 결과를 좌우한다"는 이 실험의 상위 주제를
가장 강하게 뒷받침하는 증거다.** 그리고 placebo의 우연한 오염(§4-3)은
원래 가설을 "원리5라는 특정 지식"에서 "실패-흡수 패턴을 보여주는 예시의
존재"로 한 단계 더 일반화시켰다 — 이건 계획했던 발견이 아니라 실행 중에
설계 결함을 통해 우연히 얻은 결과지만, 오히려 원래 가설보다 더 검증
가능하고 더 실용적인 형태다.

5. **격리 확인 절차 자체를 프로토콜에 명문화**: 이번에 배운 것 — "다른 파일
   찾아보지 마라"는 지시는 과제 프롬프트에만 있으면 부족하다(오염 확인
   질문 단계에서도 새는 것을 목격함, §5-2-3). 다음부터는 지시문에 기대지
   않고 **매 회차 시작 전에 `fixtures/`·`README.md`·이전 회차 산출물을
   저장소 밖으로 물리적으로 치우는 것**을 기본 절차로 삼는다.
6. **결과 파일 유실 방지**: 매 회차가 같은 파일명(`task1.py` 등)에 쓰다 보니,
   앞 회차 결과를 옮기기 전에 다음 회차가 시작되면 덮어써질 수 있다(실제로
   한 번 발생, `task2_run3` 자기보고 유실). 다음부터는 회차마다 임시
   출력 디렉터리를 분리하거나, 결과를 받는 즉시 옮긴 뒤에만 다음 회차를
   시작하는 순서를 강제한다.
7. **"원칙 이름표" vs "worked example" 자체를 독립 변수로 (§4-3에서 도출)**:
   placebo가 우연히 증명해 버린 것 — "원리5"라는 이름·서사가 없어도, 같은
   심층 구조(실패를 성공값으로 흡수하지 말 것)를 보여주는 예시 하나만
   있으면 다른 표면 주제(네이밍 관례)를 통해서도 전이된다. 다음 실험은
   이걸 의도적으로 설계해야 한다: (a) 원칙 이름표 + 무관한 예시, (b) 원칙
   이름표 없이 + 같은 심층 구조의 예시(진짜 무관한 주제로), (c) 이번
   treatment처럼 이름표 + 관련 예시 셋을 비교하면 "이름표"와 "예시"의
   기여도를 분리할 수 있다. 이번 placebo를 다시 쓰려면 사례 3(`parse_date`)을
   실패-흡수와 무관한 사례로 교체해야 한다(예: 단순 오타 사례로).

## 8. 도구·근거·한계 정리

- **선택 도구**: 최초 실행은 Claude Code `Agent` 도구로 서브에이전트 9개 병렬
  실행(`executor`, `model: sonnet` 고정). 재실행(control_clean, §4-2)은
  Agent 도구가 서브에이전트 cwd를 바꿀 방법을 주지 않아, 대신 사용자가
  WSL 터미널에서 직접 `cd` 후 새 `claude` 세션을 매 회차 수동으로 열었다.
- **선택 근거**: 이 프로젝트(`korean-subtitle-corrector`)에서 실제로 반복된
  사고를 다루는 것이라 같은 하네스(Claude Code)로 재현하는 것이 가장 직접적.
- **확인한 경계 (최초 실행)**: 프롬프트 수준의 "다른 파일 읽지 마라" 지시로는
  자동 로드되는 프로젝트 메모리(`CLAUDE.md`/`AGENTS.md`)를 못 막는다.
- **확인한 경계 (재실행, §5-2)**: cwd를 옮기는 것만으로는 부족하다 — (a) WSL
  기본 실행 경로가 cwd를 부모 폴더로 되돌릴 수 있고, (b) "다른 파일 읽지
  마라"는 과제 프롬프트에만 있으면 그 프롬프트를 받기 **전** 단계(오염 확인
  질의응답)에서는 무력하며, (c) 지시문보다 물리적으로 파일을 치우는 쪽이
  유일하게 재현 가능한 방어였다.
- **미확인 사항이었다가 이번에 답한 것**:
  - (a) cwd를 완전히 격리했을 때도 같은 방향의 결과가 나오는가 → **아니오,
    반대 방향으로 나왔다**(§6). 오염된 control은 task3만 맞혔고 task1·2는
    틀렸는데, 진짜 baseline은 task1·2를 100% 맞히고 task3만 가끔(1/5) 틀렸다.
  - (b) 표본을 늘렸을 때도 차이가 유지되는가 → **확인**. task1·2는
    control\_clean N=5에서도 흔들림 없이 5/5. task3는 control 4/5,
    placebo·treatment 각 5/5(§4-3)로, N=1보다 훨씬 미묘한 그림이 드러났다.
  - (d) treatment·placebo를 재실행했을 때 §6의 task3 유보가 어느 쪽으로
    정리되는가 → **기각 쪽으로, 그러나 예상 밖의 이유로**(§4-3). treatment가
    control보다 낫다는 표면적 결론은 맞지만, placebo도 treatment와 동률
    (5/5)이었고 그 이유가 placebo 예시의 설계 결함(원리5와 심층 구조 공유)
    이었다 — "원칙 노출"보다 "실패-흡수 패턴을 보여주는 예시의 존재"가
    더 근본적인 변수라는 재해석으로 이어졌다.
- **여전히 미확인**: (c) 토큰/시간 비용 차이. (e) §7-7에서 제안한 "이름표
  vs 예시" 분리 실험.
- **재검토 조건**: §7의 항목 중 하나라도 새로 실행되면 이 문서를 갱신한다.
