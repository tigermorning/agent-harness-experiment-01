# 실험 01 — 원칙을 어디에 놓느냐가 실패-흡수 재발률을 바꾸는가

**과제**: 모두의연구소 "AI Agent 파해치기" 캠프, [프로젝트] 에이전트 하네스 톺아보기 — "논문 가설을 내 개선 실험으로 바꾸기"
**출발 저장소**: [korean-subtitle-corrector](https://github.com/tigermorning/korean-subtitle-corrector) (한국어 자막 교정기, 룰 기반)
**날짜**: 2026-09-02

---

## 1. 불편 — 무엇을 반복해서 봤는가

`korean-subtitle-corrector`의 `docs/DESIGN_PRINCIPLES.md`(원리 5)와 `AGENTS.md`는
같은 코딩 에이전트(Claude Code)가 이 저장소에서 **같은 종류의 버그를 네 번 반복해서
심었다**고 명시적으로 기록하고 있다:

> 값 하나로 "못 물어봤다"(조회 실패)와 "물어봤더니 없더라"(정상 응답, 미등재)를
> 같이 돌려주는 함수는 언젠가 반드시 둘을 뭉갠다. — `docs/DESIGN_PRINCIPLES.md:35-39`

구체 사례 4건 (모두 같은 저장소 문서에 기록됨):

| # | 사고 | 위치 |
|---|---|---|
| 1 | 우리말샘 조회 실패가 "사전 불통"으로 과장 표시 | `docs/log-archive/2026-h2.md` §62 |
| 2 | 지역어 API 5xx 장애와 "매칭 없음"이 구분 안 됨 | `subtitle_corrector/engine/dialect.py`의 `search_dialect()` |
| 3 | 모델 응답 형식 오류가 "고칠 것 없음"으로 처리됨 | `docs/IMPLEMENTATION_LOG.md` §78 |
| 4 | 어문 규범 API 403이 "등재된 표기 없음"으로 화면에 단정 표시 | `docs/IMPLEMENTATION_LOG.md` §79 |

네 번 모두 원인이 같다: **조회 실패와 조회 성공(결과 없음)을 같은 반환값으로 뭉개는
함수**. 재발이 반복된다는 것은, 이 버그가 개별 사례 문제가 아니라 **에이전트가 새
코드를 짤 때 이 함정을 매번 새로 만나고, 매번 다르게 반응한다**는 뜻이다. 이건
개별 코드 리뷰로 막을 문제가 아니라 하네스의 "메모리 표현"(무엇을, 어디에, 어떤
형태로 컨텍스트에 두는가) 문제로 다뤄야 한다고 판단했다.

이 불편이 정말 하네스 기능(컨텍스트/메모리 배치) 때문인지, 아니면 모델이 애초에
이 판단을 못 하는 것인지는 구분해야 한다 — 실험 도중 실제로 이 둘을 가르는 관찰이
나왔다 (§5 참고).

## 2. 가설과 근거

### 가설 (반증 가능)

> 실패 흡수를 경계하는 원칙(원리 5)을 **작업 지시와 같은 자리에서 즉시 컨텍스트로
> 준 조건**은, 그 원칙 없이 작업 지시만 준 조건보다, 새로 작성한 조회 함수가
> "조회 실패"와 "조회 성공(결과 없음)"을 구분하는 비율이 높다.

반증 조건: 세 fixture 과제 중 두 개 이상에서 원칙-제공 조건이 실패-구분에
실패하면 가설은 기각된다.

### 근거와 등급

| 근거 | 등급 | 비고 |
|---|---|---|
| `docs/DESIGN_PRINCIPLES.md:35-51`, `AGENTS.md` — 이 저장소에서 네 번 반복된 사고 기록 | **1차 관찰 기록** (같은 프로젝트의 자체 문서, 학술/벤더 아님) | 이 실험의 직접 동기. 재현성 있는 카운트(4회)가 있다는 점에서 일반적 "느낌"보다 근거 강도가 높지만, 표본이 한 프로젝트·한 에이전트로 한정됨 |
| Shinn et al., *Reflexion: Language Agents with Verbal Reinforcement Learning*, NeurIPS 2023 (arXiv:2303.11366) | **[학술]** | HumanEval에서 언어 에이전트가 실패에 대한 언어적 자기 성찰(verbal self-reflection)을 축적하면 pass@1이 오른다고 보고(논문 보고 수치: GPT-4 기준 80% → Reflexion 적용 91%). **주의**: Reflexion의 메커니즘은 "같은 과제를 여러 번 시도하며 실패 후 스스로 반성문을 생성해 다음 시도에 반영"하는 것으로, 이 실험처럼 **단일 시도 전에 조직 원칙을 미리 주입**하는 것과는 메커니즘이 다르다. 이 논문은 "실패에 대한 명시적 언어화가 다음 행동을 바꾼다"는 방향성의 근거일 뿐, 이 실험 설계를 직접 검증한 근거는 아니다 |
| 이 실험 자체의 실행 결과 (§4) | **관찰(N=1/조건/과제)** | 표본이 매우 작음. 아래 한계 참고 |

## 3. 실험 설계

### 고정
- 모델: Claude (Sonnet), `executor` 서브에이전트, 모든 실행에서 `model: sonnet`으로 고정
- 과업셋: fixture 3개 (아래), 내용 사전 확정, 실행 중 변경 없음
- 토큰/시간 예산: 지정하지 않음(각 과제 1회, 1턴 완결형 — 재지시 없음)
- 작업 폴더/출력 형식: 조건별로 파일 하나만 작성하도록 동일하게 지시

### 조작 — 메모리 표현 (원리5 텍스트를 어디에 두는가)
세 조건, 과제 프롬프트는 100% 동일, 프롬프트 맨 앞에 붙는 텍스트만 다르다.

| 조건 | 프롬프트 앞부분 |
|---|---|
| **control** | 없음 (과제 지시만) |
| **placebo** | "조직 코드 리뷰 원칙"이라는 동일한 틀로, 실패 흡수와 무관한 원칙(함수 이름·docstring 관례, "네 번" 서술 구조까지 동일하게 패러디) |
| **treatment** | "조직 코드 리뷰 원칙"이라는 동일한 틀로, 원리 5 본문(구현 세부사항은 제거하고 원칙+4개 실제 사고 요약만 남긴 의역) |

placebo를 넣은 이유(예상 반론 대응): treatment가 이기더라도, 그게 "원칙 내용"
때문인지 "프롬프트가 길어져서 모델이 더 신중해진 것"(순수 길이/틀 효과)인지
구분할 수 없다. control과 placebo를 분리해 두면 이 반론을 검증할 수 있다 —
**placebo가 control과 다르지 않고 treatment만 다르다면, 효과는 내용 때문이라고
말할 수 있다.**

### fixture 3개

이 저장소의 실제 사고 3건을 재현하는 조회 함수 작성 과제. 스텁 함수(구현 불가,
시그니처만 제공)가 실패할 수 있다는 것은 docstring에 적혀 있지만, **과제 지시
문장 자체에는 실패 처리를 요구하는 말을 넣지 않았다** (넣으면 두 조건 다 통과해
버려서 조작이 무의미해짐).

| fixture | 재현 대상 | 트랩 |
|---|---|---|
| `task1_get_corrections` | §78 (모델 응답 형식 오류) | JSON 파싱 실패와 "corrections: []" 정상 응답을 구분해야 함 |
| `task2_find_dialect_matches` | `search_dialect()` 실제 버그 | 서버 5xx와 "matches: []" 정상 응답을 구분해야 함 |
| `task3_get_standard_notation` | §79 (API 403) | 헤더 누락 403과 "notation: null" 정상 응답을 구분해야 함 |

### 측정
- **주 지표(과업성취도)**: 이진 PASS/FAIL — 반환값만으로 "조회 실패"와 "조회
  성공(결과 없음/거짓)"을 호출부가 구분할 수 있는가(예외, 별도 타입, 별도 채널
  등). 코드를 직접 읽고 판정(에이전트 자기보고는 참고만, 채점 근거로 안 씀).
- **보조 지표**: 코드 줄 수(완성도 proxy), 완료까지 필요했던 추가 지시 횟수(전
  조건 0회로 고정 — 모두 1턴에 완결).
- **측정 못 한 것(한계)**: 토큰 수·정확한 소요 시간은 이 세션에서 서브에이전트별로
  노출되지 않아 측정하지 못했다. `docs/BACKLOG.md`식으로 남겨 두는 재검토 조건.

### 사전 판정식 (실행 전 확정, 결과 확인 전 기록)

> fixture 3개 중 2개 이상에서 treatment 조건이 실패-구분 없이 통과하면 가설 지지,
> 그 외에는 기각.

## 5. 실행 중 발견한 오염 — 통제가 깨진 지점

control·placebo 서브에이전트의 자기보고를 읽다가, **프롬프트에 원리 5를 전혀
주지 않은 control이 task1과 task3에서 `AGENTS.md`를 직접 인용**하는 것을 발견했다:

> "이 프로젝트(AGENTS.md)의 '실패를 성공처럼 보이게 만들지 말라' 원칙을 참고해서" — control/task1 자기보고
> "이 저장소의 `AGENTS.md`가 정확히 이 패턴을 네 번 반복된 사고로 명시하고 있고... §79가 이 함수와 거의 동일한 시나리오이기 때문입니다" — control/task3 자기보고

원인은 명확하다: 이 실험을 실행한 서브에이전트들이 이 세션(cwd =
`korean-subtitle-corrector`)에서 스폰됐고, 이 저장소의 `CLAUDE.md`가
`@AGENTS.md`로 원리 5를 포함한 `AGENTS.md` 전체를 **자동으로** 불러온다.
"이 태스크와 무관한 다른 파일은 읽지 마라"는 프롬프트 지시는 **명시적 파일
탐색**(Read/Grep)만 막을 뿐, 세션 시작 시 하네스가 자동으로 주입하는 컨텍스트는
막지 못한다. Agent 도구는 서브에이전트의 작업 디렉터리를 바꾸는 파라미터를
제공하지 않아, 이번 실행 환경에서는 이 채널을 완전히 차단할 방법이 없었다.

**이것 자체가 하네스 기능(메모리/컨텍스트 관리)에 관한 관찰이다**: 프로젝트
메모리 파일(`CLAUDE.md`/`AGENTS.md`)은 "이번 작업과 관련 없다"는 지시로는
꺼지지 않고, 조작하려는 변수(원리5 노출 여부)보다 상위 레이어에서 이미 결정돼
있었다. 즉 **"메모리 표현"을 조작하려던 실험이, 그보다 더 근본적인 다른 메모리
표현(자동 로드되는 프로젝트 컨텍스트)의 존재를 드러낸 것**이다.

### 이 오염이 결론을 얼마나 약화시키는가

원래 가설("원칙을 아예 안 준 조건 vs 준 조건")은 **엄밀하게는 검증 불가**가
됐다 — control도 사실상 원칙에 노출돼 있었다. 그런데도 결과가 여전히 의미 있는
이유는 두 가지다.

1. **오염이 균일하지 않았다.** control은 task3(§79와 시나리오가 사실상 동일)에서만
   원칙을 적용했고, task1·task2(오히려 `search_dialect()`와 더 가까운 task2
   포함)에서는 적용하지 않았다. 즉 ambient 메모리는 "인지"는 시키지만 "행동"을
   안정적으로 바꾸지 못했다.
2. **placebo/task3의 자기보고가 결정적이다**: 이 서브에이전트는 원리 5를 명확히
   인지했다고 스스로 밝히면서도 — *"이 프로젝트(한국어 자막 교정기)의 원칙을
   이 무관한 실험용 파일에까지 끌어와 반환 시그니처를 임의로 확장하지
   않았다"* — **의도적으로 적용을 억제**했다. 같은 ambient 정보를 두고
   control/task3은 "일반적으로 옳은 설계"라 적용, placebo/task3는 "프로젝트
   고유 규칙이라 범위 밖"이라 억제 — 정반대 결론이 나왔다.

즉 실제로 검증된 것은 원래 가설보다 좁지만 더 흥미로운 것이다:

> **같은 내용이라도, 그것이 "지금 이 작업에 적용해야 할 지시"로 스코프된 채
> 즉시 컨텍스트에 있는지(treatment), 아니면 배경에 있는 "그 프로젝트의 규칙"으로
> 남아 매번 적용 여부를 새로 판단해야 하는지(control/placebo)에 따라 준수율이
> 갈린다.**

treatment는 3개 과제 모두에서 다른 두 조건과 같거나 더 나았고(동률 포함 열세는
0건), 한 번도 뒤지지 않았다. 사전 판정식("2/3 이상 통과")은 이 좁혀진 해석
아래에서도 충족된다.

## 6. 판정

**사전 판정식 기준: 가설 지지 (3/3 ≥ 2/3).**

단, §5에서 밝힌 대로 이는 "원칙 유무"가 아니라 **"원칙이 어디에, 어떤 스코프로
놓이는가"**에 대한 지지로 좁혀서 읽어야 한다. 원래 의도했던 "완전한 무(無)-원칙
대조군과의 비교"는 이번 실행 환경(cwd가 원리 5를 담은 저장소 내부)에서는
확보하지 못했다.

## 7. 다음 실험에서 바꿀 것

1. **cwd 오염 제거**: `AGENTS.md`/`CLAUDE.md`가 없는 완전히 별도의 디렉터리·저장소를
   작업 디렉터리로 하는 세션에서 control을 다시 실행해, 진짜 무-원칙 베이스라인을
   확보한다. (이번 환경의 Agent 도구는 서브에이전트 cwd를 바꾸는 파라미터가
   없었다 — 별도 터미널 세션이나 별도 프로젝트 폴더에서 직접 재현 필요.)
2. **표본 확대**: 과제당 1회는 우연을 배제하기 어렵다. 과제당 3~5회 반복해 비율로
   비교.
3. **토큰·시간 계측**: 이번엔 노출되지 않았다. API를 직접 호출하는 방식으로
   바꾸면 `usage` 필드로 토큰을 정확히 잴 수 있다.
